# 五段录像在现有C++视觉程序中的离线基线

2026-10-07。当前步骤是先检查和修正参考线识别，暂时不继续固定档位采集，也不启动手推自动调舵。原始记录中的方向核对已经完成，视觉可靠性尚未完成。

## 已完成的实际工作

用当前src/vision.cpp及相关源码重新编译build/vision_stream.exe，逐段重启跟踪状态，将五段615帧全部输入实际C++视觉核心。统一以GarageReverse作为观察阶段，显式PERCEPTION_ONLY，不执行任务状态机更新；全615条输出speed=0、steer=0。本地回放没有硬件设备访问。

tools/replay.py增加--frame-times，直接读取各段frames.csv的elapsed_s，避免把实际约5Hz录像按标称20fps或图片目录默认20Hz生成时间。没有伪造里程、速度或IMU航向；本模式与--telemetry互斥，并保持仅观察。每段使用其保存的vehicle_config.ini，处理尺寸为配置中的320×240，与现有车载处理一致。原始文件哈希全部保持不变。

五段每段输出123帧，输出时间与原frames.csv逐项相等。原AVI内JPEG用于原帧证据；仅回放输入在内存中按原处理流程缩放，不编辑原始图像。

## 发现的问题

| 记录 | 帧数 | 线评分达到0.35的帧数 | garage输出真 | stripe输出真 |
|---|---:|---:|---:|---:|
| 前推0 | 123 | 119 | 0 | 7 |
| 前推+5 | 123 | 96 | 0 | 0 |
| 前推-5 | 123 | 104 | 0 | 2 |
| 后推+5 | 123 | 91 | 0 | 3 |
| 后推-5 | 123 | 33 | 0 | 1 |

上表只是程序评分和标志的出现次数，不是正确识别率。garage=0符合本批黑白录像不能触发旧蓝色车库条件的限制；stripe出现也没有经过停车虚线身份核对，不能直接当作库口或停车事件。

明确复核的失败案例：前推0录像frame_index=10、elapsed=2.747153138秒。原帧中同一图像行y=600的主线在约x=712；C++blackPath在对应缩放行y=200输出x约292（折回原1280宽度），相差约420像素，但line_confidence=0.93793。原主线人工可见，限定主线区域的像素候选也与712一致。说明当前较高评分不能保证跟踪的是正确参考线。

前推0第60帧也有相似诊断：原场景主线候选约770.5，而程序该行约256，评分0.95862；该条作为后续复核线索，不作为本批所有帧都已有人工真值的声明。所有逐帧原始程序输出保存在各记录同名jsonl，summary.json保留统计、实例及源码/可执行文件哈希。

已有源码以黑色扫描候选和局部预测匹配，并主要用行命中数量作为confidence。暗区、阴影、褶皱或分支形成的连续候选可能得到较高评分；当前结果明确证明存在错选参考区域，但本轮没有逐像素穷尽区分每类成因。不能只调高评分门槛，因为0.94以上仍发生错误。

## 现在做什么

用户暂时不需要推车、测角或重新录像。下一步修改参考线选择和身份跟踪：利用线宽、两侧对比、跨行几何一致性及跨帧身份，对交点处的主线与分支分别处理；没有可靠对应时输出不确定，不用另一条线或背景填补。

修正后优先重放同一615帧，先确认上述高评分错误案例被修正或被拒绝，再检查主线退出视野、遮挡及倒车分支变化。与原帧人工对应后才安排仅舵机的手推闭环；图像特征通过后还需独立验证厘米/角度位姿，不能用未标定的像素斜率直接生成实际角度。

生产视觉源码、车辆配置、舵机输出逻辑本轮没有改变。新增回放时间输入只用于离线检查；尚无新的板上闭环程序需要上传。详细后续要求见../VISUAL_STEERING_NEXT.md。

## 本轮修改代码的五项检查
